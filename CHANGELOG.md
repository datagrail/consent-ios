## [Unreleased]

### Added

- `initialize(configUrl:onConfigError:completion:)` (TRUST-3254). When a config fetch fails but a cached config is served, `onConfigError` receives the failure (`.configNotPublished`, `.httpError`, `.networkError`, `.parseError` for any body that is not a config, or `.validationError`) once, on the main queue, before `completion`. It is not called on success, on a 304, or when nothing is cached (`initialize` then fails as before). It is not called for a session that `reset()` or a later `initialize` has superseded. Matches consent-react's `onConfigError` `initialize` option (TRUST-2745): the handler applies to that `initialize` call only, not to later ones.

- **Breaking:** `ConsentError.configNotPublished(statusCode:)`. A config fetch rejected with a definite 4xx (any 4xx except 408 and 429, including 403) when no cached config exists now fails with `.configNotPublished` instead of `.httpError`, and is not retried. With a cached config, the cache is still returned. Host apps that switch exhaustively over `ConsentError` must add the new case. Same name and trigger as Android `ConsentException.ConfigNotPublished` and React `CONFIG_NOT_PUBLISHED`.
- `Logger.error` on every config-load failure (fetch, parse, validation, 304 with no cache, cache write) and on `initialize` failure. Visible when `DataGrailConsent.logLevel` is `.error` or higher.
- Demo app: a **Config URL** tab that loads a pre-signed test config link from the Mobile tab and previews it with the SDK's banner, showing the SDK and config schema versions and a specific error for expired, altered, deleted, unreachable, unparseable, or unsupported-schema links. Demo-only; the SDK's public API is unchanged.
- `clearUserIdentifier()` — logout / return-to-neutral for Universal Consent (TRUST-2902). Clears the device's identity binding, returns local consent to the config default (banner shows again) and fires the consent-changed listener. Non-destructive, unlike `reset()`: no network call, the server-side record is untouched, and the unique id, config cache, version, locale and pending queue are kept. The SDK cannot detect a logout it is not told about, so hosts must call this on logout.
- `setCcpaOptout(_:completion:)` and `getCcpaOptout()`: a first-class CCPA/CPRA "Do Not Sell or Share" choice (TRUST-2591). iOS has no native DNSMPI signal, so the host app is the source of truth. The flag is stored on the device and never changes a category. It is written through to the user's Universal Consent record when Universal Consent is enabled, `universalConsent.sync_optout` is on, `setUserIdentifier` has succeeded in this app session, and an explicit consent choice is stored. Otherwise it rides the next Universal Consent write. A choice made while signed in, or during a login, that has not reached the record yet (nothing to write it with, a failed write) is kept by a re-sync or rehydrate instead of the record's older value.

### Changed

- Fetched configs are now validated with `ConfigValidator` before being cached. An invalid config falls back to the cached config, or fails with `.validationError` if none exists, and is not retried.
- `ConfigValidator` (public) now accepts `ConsentLayerLanguagePickerElement` and applies per-type translation rules: link elements need non-empty `links`, each with translations; category, language picker, tracking details, and browser signal notice elements don't need top-level `translations`. Previously it rejected real published configs.
- A config-cache write failure no longer discards a freshly fetched, valid config.
- **Behavior change (TRUST-2591):** Universal Consent writes now include `ccpa_optout`, set from the user's stored choice (`setCcpaOptout`) and gated by `universalConsent.sync_optout`. iOS used to omit the field. The value is never derived from a category or ATT. When a login finds a record, the record's `ccpa_optout` replaces the local flag. On a re-sync it is adopted only when `sync_optout` is on, and not while a choice made while signed in has yet to reach the record. `clearUserIdentifier()` resets the flag to `false` and `reset()` wipes it. Records written earlier are adopted as they are.
- `setUserIdentifier` login rule (TRUST-2902). The device now persists the user hash (never the raw identifier) of the identity it is bound to, cleared by `reset()` and `clearUserIdentifier()`. On a login (device unbound or bound to a different identity): if a record is stored it replaces local state (categories the record omits take their config default, never the prior local value; a record carrying no consent choice returns local state to neutral) and nothing from the device is written, even when a pre-login choice exists; if no record is stored, an explicit local choice (one the user saved on this device while it was not bound to a different identity) seeds the new record, and config defaults are never written. State left by a different bound identity is not written and local state returns to neutral. Once bound, a re-sync with no local change since the last sync adopts the record and writes nothing, so it never re-sends a choice the user didn't change over a newer one from another device. A local change since then (any `savePreferences`, including one made while a sync's read or write was in flight) is written as the user's raw choice. The device persists what the last sync left (the stored and raw consent maps and the bound user hash, never the raw identifier), so this also holds after an app relaunch and a view that ATT, GPC or the record's `ccpa_optout` suppressed is never written over the user's cross-device opt-ins. That state is cleared by `clearUserIdentifier()`, `reset()` and an identity switch. `rehydrateFromUniversalConsent` for the bound identity records what it stored the same way, so a later re-sync or `setCcpaOptout` never writes the view it suppressed; for any other identity it clears that state. A `clearUserIdentifier()` or `reset()` during its read now supersedes it: nothing is stored and it fails.
- `setUserIdentifier` with nothing to write now succeeds without writing, instead of failing with "No consent preferences to sync". The lower-level `ConsentManager.setUserIdentifier(_:apiKey:preferences:...)` write keeps that validation.
- **Breaking (wire):** signing format (TRUST-2971). Signed Universal Consent writes now bind provenance into the HMAC `stringToSign` as a 5th `provDigest` segment (`ConsentService.provenanceDigest(...)`). This changes the signed-string layout, so it **must not be released until the consent-backend verifier that reconstructs the 5-segment string is live at the edge** (the verifier landed in consent-backend #1040). Shipping this SDK first would make every signed write fail verification in production.
- Limitations: the SDK cannot tell whether a pre-login choice was made by the person logging in or by a previous user of a shared device (on a no-record login it attaches an explicit unbound choice by design), does no heuristic shared-device/shared-account detection, and cannot detect two people sharing one account.

### Fixed

- A `setCcpaOptout` choice made while signed in but before `setUserIdentifier` re-ran in this app session (for example right after a relaunch) now reaches the Universal Consent record. Before, the next re-sync kept it locally but, with no category change to write, never sent it. The re-sync now writes it as a CCPA-only write (no `cookieOptions` category, so no category on the record changes at any stamp), stamped with when `setCcpaOptout` was called (stored next to the flag), so it ranks against the record's `ccpa_optout` by when the user chose rather than by when it was finally sent (TRUST-2591, TRUST-2902)
- **Behavior change (TRUST-3223):** a stale device's Universal Consent re-sync no longer undoes a newer choice made on another device (the P0-06 sign-off scenario: choose on this device, revoke on the web, re-sync here, and the grant came back). The SDK now stores the time of each consent choice next to the stored preferences (an adopted record takes the record's `updated_at`; removing the stored choice clears it) and sends it on every write as `is_explicit: true` plus `decision_ts`, signed into `provDigest`. A re-sync writes a local change over a found record only when it was made strictly after the record's `updated_at`; otherwise the record is adopted. A choice stored before this release has no recorded time, so it adopts a found record rather than overwrite it, and a write with no known time sends no provenance (byte-identical to before). Same rule as consent-banner TRUST-3154. A `setCcpaOptout` write-through, like the pending-CCPA flush, is a **CCPA-only** write (TRUST-2591 decision, 2026-10-26, same body as consent-banner #756). It sends `ccpa_optout` with its provenance and an empty `cookieOptions` map, with no `isCustomised`, `consent_mode`, `platform`, `policy_name` or `config_version`, and it is stamped with when the CCPA choice was made. It never resends the category map, so it cannot out-rank a newer revocation (TRUST-3311). An unsynced local category change with a known decision time goes first, in its own write at its own time, as consent-banner #756 does, so the CCPA write's newer `updated_at` cannot make the next re-sync adopt over it. With `sync_optout` off, `ccpa_optout` is left out of every write instead of being sent as `false`, and a choice made meanwhile stays pending until the gate turns on (TRUST-3381). `ConsentStorage.saveCcpaOptout` now also clears the stored CCPA decision time; hosts should use `DataGrailConsent.setCcpaOptout`. A login that finds a record adopts its `ccpa_optout` whatever `sync_optout` says. Before, it re-sent the categories with their older stamp, which tied the record's `ccpa_optout` right after an adopt, and the edge keeps an opt-out on a tie, so clearing an adopted opt-out never reached the record.
- **Behavior change (TRUST-3223):** after a re-sync writes a local change over an older found record, this device keeps that change locally. Previously local state took the older record until the next sync, so a category the user had just turned off on this device read as enabled again.
- A `savePreferences` call made while a re-sync's read is in flight is no longer replaced by the record. The re-sync keeps it and writes it, with its own decision time, instead of the choice stored before the read (TRUST-3223). A kept local choice also keeps the config version it was made under, so a later config version bump still re-prompts.
- A `savePreferences` call that lands after a re-sync has stored the record it read, but before the re-sync finishes, is now written by that re-sync, as one made during the read is. Before, it was left for the next re-sync, and a logout in between meant the record never got it (TRUST-3223). A save made during the read that equals the record's choice sends nothing and keeps its own decision time. When such a save has to be stamped after a record from a device whose clock is ahead, the stamp is capped one second past the edge's future clamp (now + 300 s). If the edge can still keep the record on a tie, the save is not recorded as synced, so the next re-sync writes it again.
- `initialize` now always delivers its completion on the main queue, on both success and failure.

## [1.7.0] - 2026-08-25

### Added

- Universal Consent (cross-device consent) support — opt-in `setUserIdentifier`, `fetchUniversalConsent`, and `rehydrateFromUniversalConsent` (both signed and api-key-only variants), plus a 30s ceiling on the customer-provided `getSignature` callback.

### Changed

- **Breaking:** `ConsentError` — non-2xx HTTP responses now surface as `.httpError(statusCode:message:)` instead of `.networkError`; adds the new `.httpError` and `.signatureTimeout` cases. Host apps that switch exhaustively over `ConsentError` must add the new cases. Breaking but low-impact, so shipped as a minor bump.
- Retry policy — a definite 4xx (other than 408 and 429) is no longer retried on config fetch, `savePreferences`, and `saveOpen`; it fails after one attempt. 408, 429, 5xx, and transport failures still retry.
- `rejectAll()` now treats a category as essential if `alwaysOn` is true OR its `gtmKey` contains "essential" (aligning with the banner's definition), so such a category stays enabled after reject-all instead of being disabled.
